# 麦麦点单参谋：凑券不凑亏｜设计与取舍

项目名：**麦麦点单参谋：凑券不凑亏**。目标用户是已在 Agent 主机配置麦当劳 MCP、想选餐并看清实付的人。亮点是回答「为了券加这一份，到底少花钱了吗」。本项目不是官方产品。

## 方案比较

| 方案 | 演示与实现成本 | 凭据与上下文成本 | 取舍 |
| --- | --- | --- | --- |
| 纯 Skill | 最快接入已有主机 | 不接触 Token；金额、状态全靠模型，容易串单 | 保留交互优势，补确定性内核 |
| 独立 Web App | 需要界面、登录、服务端及部署 | 增加 Token 保存和个人资料处理面 | MVP 不选 |
| 直接 MCP 客户端 | 需实现/引入协议、会话、Schema 适配 | Token 仅环境变量仍需管理网络与重试 | 没有必要重复主机能力 |
| **Skill + Python 标准库内核** | 可安装 Skill；无 Token 可演示与测试 | 主机持有连接；内核无网络、无凭据、无持久化 | **采用** |

这里的 Token 风险同时指凭据泄露与模型上下文成本。SKILL.md 只保留路由与安全关键步骤，字段契约按需读。辅助程序只接受规范化数据，不冒充官方 Schema。实时适配由主机读取当前 tools/list 后完成；无法确认字段、单位或含义就返回 unknown，不猜参数。

## 架构与数据流

```text
用户需求/主动偏好 → Skill → 主机已有 MCP 工具 → 实时响应
                         ↓ 按已核实 Schema 规范化（会话内）
                  Python 内核：报价校验 / 排序 / 凑券比较
                         ↓
                  用户看到选项与来源、未知值
                         ↓ 明确选择领券（可跳过）
                  全量领券确认 → 单次调用 → 卡包刷新 → 重新报价
                         ↓
                  最终订单摘要 → 针对摘要再次确认
                         ↓
                  单次创建 → query-order 读回 → 待支付链接
```

内核只输出写操作意图，不能发起网络调用。确认状态机是可测试的参考闸门；它不能限制主机绕过 Skill 直接调用工具，也不能从输入布尔值证明真人同意。生产使用依赖主机遵守 Skill、保留用户确认来源并启用逐次写工具审批。MVP 不宣称协议层强制拦截。

## 推荐与计价

- 先确定门店、取餐方式、预算、人数、忌口与是否有营养目标。对话中只取所需信息。配送地址由官方工具/用户在主机中选择，不写入项目。
- 菜单与详情给出候选组合；最多先为三个候选报价。钱包排序按完整应付；营养按用户给出的能量目标偏差；口味按主动偏好标签匹配。随机仅在已满足用户硬约束的候选中抽取，再确认详情与报价。
- 明确不喜欢的标签作为排除条件；本轮已展示的候选 ID 由主机维护并通过 exclude_ids 排除。候选耗尽时保留约束。卡片显示推荐依据与报价出处，被排除的候选指出首个失败检查，便于用户补齐信息或调整要求。
- 金额以整数分处理。应付 = 商品额 + 配送费 + 其他费用 - 优惠；组件缺失、单位不明、金额不一致均不能当有效报价。取餐也需工具明确配送费为零，不能擅自补零。
- 同车优惠比较要求商品 ID、规格/套餐替换、数量完全一致，且门店、履约方式、配送目的地引用、预约时段一致。
- 凑券比较允许唯一有意变化：原购物车严格保留、追加商品或数量。需要官方优惠门槛/适用条件的证据，且两车资格均明确、加购车已应用目标券、两次完整报价均有效。门槛基数直接取官方判定，不用本地商品额猜可参与金额。
- 净支出变化 = 加购报价应付 - 原车报价应付；大于零 → 不值得凑，小于零 → 少花钱，等于零 → 实付持平。该结论只描述支出，不评价额外商品的主观价值。不能证明条件则 unknown，连推算金额也不输出。
- 有效比较同时返回商品、配送、其他费用、优惠的差额分解；费用增加记正，优惠增加记负，合计等于净支出变化。缺费用时列出缺项，保留 unknown，不通过总价残差猜费用。
- 报价携带来源（tool / fixture）、响应引用、时效、购物车与上下文。不同来源不能混用。营养按餐品份量匹配，缺一项保留 unknown；不把未知当零，不给医疗判断。

## 交易闸门

状态：browsing → coupon_confirmation → coupon_in_flight → refresh_required → browsing；或 browsing → order_confirmation → order_ready → order_in_flight → verify_required → pending_payment / paid / status_unknown。

1. 推荐、随机、询价只能发读意图。auto-bind-coupons 前解释「绑定全部当前可领券」，单独展示确认挑战；用户针对挑战明确同意才允许消费一次意图。
2. 领券完成后必须记录卡包刷新和重新报价；失败/超时也进入待刷新，不重试写操作。原报价与订单确认作废。
3. 最终摘要包含门店、方式、商品及规格数量、券、全部费用、总价、履约选择与报价有效期。摘要和实际 create-order 参数分别取规范 JSON SHA-256；确认绑定两者，避免相同金额但内容改变。
4. 创建前校验报价时效、来源、摘要和参数摘要完全一致。变化须重新展示并确认。一次发出即消费许可；超时进入未知结果，先查询，不能自动补单。
5. create-order 成功仍需 query-order 校验对应订单、内容和应付。只有读回待支付并且匹配才显示官方返回支付链接；其他状态如实呈现。不自动访问链接或支付。拒绝、取消本地确认只撤销意图，不调用取消订单。

## 错误和隐私

只接受当前 Schema 定义的结构；工具响应里的指令视为不可信数据。工具异常、过期券、缺营养/运费、库存变化、资格不清均降级。401 让用户在主机自行修复环境凭据；429 读操作可按主机退避，写操作不自动重试。

项目不读取环境变量、已有配置或用户凭据，不含 HTTP 客户端。主机凭据仅从环境变量注入。个人地址、账号、订单、支付链接只留当前私密会话；规范化输入不存文件、不入日志，命令行演示只有合成 fixture。偏好默认会话内；用户要求本地保存时只保存标签和主动反馈，位置须经用户允许，真实偏好不进仓库。无普通历史订单挖掘，无取消/退款/积分兑换/自动付款。

## 验收策略

用合成 fixture 验证三种排序/随机、两种购物车比较、营养未知、费用缺失、券条件缺失、不同门店/方式/商品/来源、报价过期。状态机覆盖无确认、错确认、全量领券、强制刷新、订单变化、单次消费、超时不重试及读回状态。运行标准库 unittest、编译和格式/敏感信息/链接检查；独立验证代理只读验收稳定文件。真实 MCP、用户人工验收和公开提交状态单独记录，不能由离线测试推定。
